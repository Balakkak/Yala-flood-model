# วิธีการและข้อจำกัดของแบบจำลองน้ำท่วม — เทศบาลนครยะลา

เอกสารนี้อธิบาย **วิธีการ พารามิเตอร์ และข้อจำกัด** ของตัววิเคราะห์น้ำท่วมในระบบ
อย่างตรงไปตรงมา เพื่อให้ตรวจสอบได้ (auditable) และไม่สื่อความแม่นยำเกินจริง

> **สรุปสั้น:** นี่คือเครื่องมือระดับ **screening (คัดกรองเบื้องต้น)** บน DEM 30 ม.
> ใช้บอก *ลำดับท่วมก่อน-หลัง · ทิศทางน้ำ · พื้นที่เสี่ยงสัมพัทธ์* ได้ดี
> **ยังไม่ใช่** แบบจำลอง hydrodynamic ที่พยากรณ์ระดับน้ำ/ความลึกเชิงสัมบูรณ์แบบแม่นยำ

---

## 1. วิธีการ — Priority-Flood (minimax connectivity)

มองว่าระดับน้ำค่อย ๆ ยกตัวขึ้นจาก "แหล่งน้ำ" (แม่น้ำปัตตานี + ทางน้ำจริง/`channel`)
สำหรับทุกเซลล์ของ DEM หา **arrival level** = ระดับน้ำต่ำสุดที่ทำให้เซลล์นั้นเชื่อมต่อ
(hydraulically connected) กับแหล่งน้ำผ่านเส้นทางแบบ minimax:

```
arrival[neighbour] = max( arrival[current], elevation[neighbour] )
```

คำนวณด้วย priority queue (min-heap) — คล้าย Dijkstra แต่ใช้ max ตามเส้นทางแทน sum
ผลลัพธ์:
- **ลำดับท่วมก่อน-หลัง** — เซลล์ arrival ต่ำ + ติดแหล่งน้ำ → ท่วมก่อน
- **ทิศทางการไหล** — D8 ตาม gradient ของ arrival
- **ความลึก ณ ระดับน้ำผิว S** — `depth = S − elevation` เฉพาะเซลล์ที่ `arrival ≤ S`

โค้ด: [`assets/flood_analysis.js`](../assets/flood_analysis.js) (รันไทม์ในเบราว์เซอร์)
และ [`scripts/validate_model.js`](../scripts/validate_model.js) (ตรวจสอบความถูกต้องแบบ headless)

## 2. ข้อมูลนำเข้า

| ชั้นข้อมูล | แหล่ง | บทบาท |

### ความแม่นยำของ DEM (ตรวจสอบจริง)
เทียบ DEM กับ **ICESat-2 ATL08** (LiDAR จากดาวเทียม, 3,924 จุด):

| ตัวชี้วัด | ค่า |
|----------|-----|
| ส่วนเบี่ยงเบนแนวดิ่ง (std) | **±5.45 ม.** |
| จุดที่คลาดเคลื่อน < 2 ม. | 47% |
| datum offset | −13.91 ม. |

(ดู [`data/dem_validation_icesat2.json`](../data/dem_validation_icesat2.json))

## 3. พารามิเตอร์ปรับเทียบ (calibration) — รวมศูนย์ที่ `flood_analysis.js`

เพราะ DEM มี error ±5 ม. การคิด % พื้นที่/ความลึกจากค่าดิบจึงไม่น่าเชื่อถือ
ระบบจึง **ปรับเทียบค่าที่แสดง** ให้สอดคล้องกับเหตุการณ์จริง (AAR พ.ย. 2568) แทน
ค่าทั้งหมดอยู่ในบล็อก `CALIBRATION & MODEL CONSTANTS` ที่เดียว:

| พารามิเตอร์ | ค่า | ที่มา / เหตุผล |
|-------------|-----|----------------|
| เกณฑ์ตลิ่ง (base stage) | 14.0 ม.รทก. | ระดับตลิ่งแม่น้ำปัตตานี |
| เริ่มท่วม (onset) | 15.25 ม.รทก. (+1.25) | flood_response.py |
| เหตุการณ์ พ.ย.2568 | 18.25 ม.รทก. (+4.25) | AAR เหตุการณ์จริง |
| `FLOOD_THRESHOLDS.RAIN_MMH` | 30 mm/hr | เกณฑ์น้ำท่วมฉับพลัน |
| `FLOOD_THRESHOLDS.STORAGE_PCT` | 90% | เขื่อนบางลางเสี่ยงล้น |
| `FLOOD_THRESHOLDS.RELEASE_MCM` | 200 m³/s | ระบายแล้วเสี่ยงท้ายน้ำ (ปกติ <50) |
| `RUNOFF` (Rational Q=C·I·A/3.6) | C=0.75, A=21 km² | เมืองกึ่งปิดผิว, ลุ่มน้ำเมืองยะลา |
| `DURATION` gain (24ชม.→3วัน→7วัน) | 0.25 / 0.25 / 0.18 | ยิ่งนานน้ำยิ่งแผ่/สูงเล็กน้อย |

> ค่าเหล่านี้คือ "สมมุติฐานที่ตั้งโดยมนุษย์" — เปลี่ยนได้เมื่อมีข้อมูลดีกว่า
> นี่คือจุดที่ผู้ตรวจควรถาม และเราตอบได้ว่าอ้างอิงจากอะไร

## 4. การตรวจสอบความถูกต้อง (validation)

รันด้วย `npm test` → [`scripts/validate_model.js`](../scripts/validate_model.js)
เทียบ arrival ของโมเดลกับ **ground truth อิสระจาก GISTDA** (ซ้อน 3 ชุด → 0–3 แหล่งยืนยัน):
ภาพน้ำท่วมดาวเทียม (โพลิกอน) + จุดน้ำท่วมริมตลิ่ง + แนวน้ำล้นราชการ

ผลล่าสุด (เซลล์เมือง 26,195 · GISTDA ทับ 14.6%):

| ตัวชี้วัด | โมเดล | baseline (ความสูงล้วน) | ความหมาย |
|----------|-------|------------------------|----------|
| ROC-AUC (≥1 แหล่ง) | 0.75 | 0.76 | แยกพื้นที่เคยท่วมได้ดีกว่าเดาสุ่มชัดเจน |
| ROC-AUC (≥2 แหล่ง) | 0.82 | 0.83 | ยิ่งหลายแหล่งยืนยัน ยิ่งแม่น |
| Spearman ρ | −0.31 | — | arrival ต่ำ ↔ ท่วมบ่อย (ทิศทางถูก) |

**การตีความอย่างตรงไปตรงมา:**
- โมเดล **ดีกว่าการเดาสุ่ม (0.5) อย่างมีนัย** — จับพื้นที่เสี่ยงได้จริง
- แต่ที่ความละเอียด 30 ม. โมเดล connectivity **เทียบเท่า (ต่ำกว่าเล็กน้อย)** การจัดอันดับ
  ด้วยความสูงล้วน — สะท้อนว่าที่ scale นี้ความสูงเป็นตัวขับหลัก ส่วน connectivity
  ให้คุณค่าด้าน *ทิศทาง/ลำดับ* มากกว่าความแม่นเชิงพื้นที่
- FAR สูง (โมเดลเตือนเกินขอบเขต GISTDA) ส่วนหนึ่งเพราะ ground truth ครอบคลุมแค่ 14.6%

ค่ากำกับไว้ที่ [`data/validation_result.json`](../data/validation_result.json) (อัปเดตทุกครั้งที่รัน test)

## 5. ข้อจำกัดที่ทราบ (ต้องแจ้งผู้ใช้/ผู้กำหนดนโยบาย)

1. **ไม่ใช่ hydrodynamic จริง** — ไม่มีสมการ shallow-water, ไม่มีอัตราการไหล/ฝน/
   การระบายเป็นฟังก์ชันของเวลา การไล่เวลาบนไทม์ไลน์เป็น *pacing* ตามลำดับท่วม ไม่ใช่นาฬิกาจริง
2. **DEM 30 ม. + ±5 ม. แนวดิ่ง** — มองไม่เห็นซอย คูคลองเล็ก กำแพงกันน้ำ คันถนนย่อย
   ความลึกสัมบูรณ์จึงเป็นค่าปรับเทียบ ไม่ใช่ค่าวัด
3. **ระบบระบายน้ำเป็น heuristic** — หักความจุระบายแบบประมาณ ไม่ใช่แบบจำลองท่อ (SWMM)
4. **ต้นน้ำฝั่งตะวันออกเป็นค่าประมาณ** (`yala_eastern_inflow`) รอข้อมูลคลองจริงจากเทศบาล
5. **ground truth ครอบคลุมบางส่วน** (14.6% ของเซลล์เมือง) — metric จึงเป็นภาพคร่าว

## 6. แผนพัฒนาต่อ (roadmap)

ระบบนี้คือขั้น **"เดินได้ก่อน"** ก่อนต่อยอดเป็นแบบจำลองเชิงวิศวกรรม:

1. **LiDAR DEM (±0.15 ม.)** — แทน DEM 30 ม. → ทำความลึก/ขอบเขตน้ำท่วมแม่นจริง
2. **HEC-RAS 2D** — แบบจำลอง shallow-water แบบมีเวลาจริง (อัตราการไหล, hydrograph)
3. **EPA SWMM** — ระบบท่อระบายน้ำเมืองเป็นฟังก์ชันของเวลา
4. **ข้อมูลท่อ/คลองจริงจากเทศบาล** — แทน heuristic ปัจจุบัน

มี [`lisflood/`](../lisflood/) (LISFLOOD-FP 2D) เป็นก้าวกลางระหว่างทาง — ผลลัพธ์ที่
render แล้วแสดงผ่าน viewer ในแดชบอร์ด
